Architecture · Import service

How should we structure the services?

Contacts, Import, and Billing all need to ship. The question is how independently they deploy and own data.

✓
Option A

Monolith

One codebase, one deploy, one database. Simplest to build and run; everything scales together.

✓
Option B

Modular monolith

One deploy, but enforced module boundaries inside. Clean seams now; can split out later.

✓
Option C

Microservices

Each domain deploys and scales on its own DB. Most flexible; most operational overhead.

How does an import job actually run?

A CSV can hold tens of thousands of rows. The question is what happens between the user clicking “Import” and the data landing.

✓
Option A

Synchronous

API parses and writes during the request. Dead simple; the user waits and big files can time out.

✓
Option B

Worker + queue

API enqueues and returns immediately; a worker processes in the background. Scales to huge files; more moving parts.

✓
Option C

Scheduled batch

Uploads collect and process on a schedule. Cheap and steady; data isn’t live until the next run.
