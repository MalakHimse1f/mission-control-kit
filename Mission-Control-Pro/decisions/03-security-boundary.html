The cloud can tell the bridge to spawn local processes.
How much defense do we put around that?

The problem The bridge daemon executes commands on the user's machine in response to cloud events. If a stolen token, a compromised relay, or a buggy server can send a malicious payload, we are a remote-code-execution vector — the most attractive attack surface in the product. We need to pick a mitigation posture before any code ships.
Decided 2026-05-26 · Path C

Defense in depth — all five mitigations required. Signed envelopes, hard-coded spawn allowlist (Claude only), first-run workspace consent, per-device + per-org kill switch, append-only audit log. Threat model document required before protocol implementation begins.

Decision

What security envelope wraps every cloud → bridge command?

A Not chosen
Minimal — TLS + auth token only
Cloud and bridge talk over TLS WebSocket. The bridge accepts any well-formed event from an authenticated session. Trust the server.
Attack surface
Cloud — signs nothing
↓ tls + bearer
Bridge — accepts anything
↓
spawn(*)
Pros
  • Simplest to ship
  • No key management
Cons
  • One stolen token = RCE on every paired device
  • Any cloud breach is catastrophic
  • No replay protection
  • Will fail any enterprise security review
B Not chosen
Signed envelopes — payloads carry a server signature
Every cloud → bridge command is wrapped in a signed envelope (nonce, expires-at, signature). Bridge holds the cloud's public key from install and verifies. Replay-protected.
Signed envelope flow
Cloud — signs each event
↓ envelope + sig
Bridge — verifies + nonce check
↓
spawn(*) — anything allowed
Pros
  • Server breach can't be replayed
  • Token theft doesn't enable RCE on its own
  • Reasonable enterprise posture
Cons
  • Compromised signing key still = RCE
  • No defense against malicious command shapes (`rm -rf`)
  • No user awareness of what's running
C Decided
Defense in depth — signed envelopes + allowlist + consent + kill switch + audit
All of Path B, plus: bridge will only spawn programs on a hard-coded allowlist (claude); first time any workspace path is targeted, the tray prompts the user for consent (persistent); admins can kill any device or the whole org; every spawn is appended to an audit log.
Five overlapping checks
1. Signed envelope verified
2. Nonce + expiry checked
3. Program ∈ allowlist (claude)
4. Workspace path approved
5. Spawn audited + revocable
Pros
  • No single failure causes RCE
  • User is in the loop the first time
  • Org admin has real-time controls
  • Passes enterprise security review confidently
  • Audit log enables incident response
Cons
  • More plumbing — protocol + tray UX + audit table
  • First-run consent adds one extra click
Implementation notes if Path C is chosen Bridge spawn allowlist is compiled in, not configurable from cloud. Workspace consent persists in the bridge's local SQLite; revoking it requires user action in the tray (or org admin kill-device). Audit rows include: device_id, command, workspace_path, signature_kid, envelope_nonce, result. Threat model document required before protocol implementation begins.
