"Respond with structure" on mobile spans approve buttons to PRD reviews.
What does the phone actually render?

The problem Some decisions are tap-once on a phone ("approve next stage"). Others are 800-word PRD reviews that no one wants to read on a 6-inch screen. We need a schema that tells the mobile app which decisions it can render and which it should kick to web.
Decided 2026-05-26 · Path B

Render anything best-effort. Workflow authors can specify any response shape; mobile renders it and the user can escape to web or local for richer review. Decision shape is open, not a closed enum. Long content gets a scrollable view or an "Open in web" link — but the choice belongs to the user, not the schema.

Decision

What's the contract between workflows and the mobile app?

A Not chosen
Fixed schema set — mobile renders only what it knows
Workflow author picks one of N defined response types: approve, choose-one, choose-many, short-text. Mobile knows how to render each. Anything else can't exist as a workflow step.
Schema enumeration
✓ approve / reject
✓ choose-one
✓ choose-many
✓ short-text (≤200)
✗ everything else
Pros
  • Mobile experience is always good
  • No "this looks broken on phone" surprises
Cons
  • Workflow authors hit a hard wall
  • PRD review, diff review impossible to express
B Decided
Render anything — let mobile try its best
Workflow can specify any response shape. Mobile tries to render it; falls back to "Open in web" for anything that doesn't fit.
Best-effort rendering
decision: arbitrary shape
↓ mobile inspects
Can I render this? (heuristic)
Yes → render
No → "Open in web"
Pros
  • Flexible for advanced workflows
Cons
  • "Open in web" feels like a failure
  • Heuristics are unpredictable
  • Mobile dev complexity explodes
C Not chosen
Schema set + explicit escape hatch
Path A's fixed schema set is the only mobile-renderable shape. Workflow authors can additionally declare a step as kind: web-only — mobile sees it but shows "Open in web." No surprises on either side.
Two clear lanes
Mobile-friendly: approve / choose / text
↓ renders on phone
Web-only: long-form, diff, picker
↓ mobile shows: Open in web
Either way: notification works
Pros
  • Mobile UX always good for supported types
  • Authors aren't blocked from rich web flows
  • Push still notifies for everything
Cons
  • Authors must consciously pick web-only
Implementation notes if Path C is chosen Decision schemas live in @mcp/schema as Zod, shared by workflow DSL parser, web renderer, and mobile renderer. Add type discriminator: kind: 'approve' | 'choose-one' | 'choose-many' | 'short-text' | 'web-only'. Mobile validates incoming decision against schema and renders the matching component.
