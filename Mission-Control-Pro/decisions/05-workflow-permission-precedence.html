Permission Groups and Teams are two different things.
Previously conflated — now split.

The original framing I had treated "Permission Groups" as one mechanism that did both jobs: governing org-config access AND grouping users for workflow assignment. That was wrong, and it generated a precedence puzzle that turned out to be artificial. The correction is to recognize these as two independent axes.
Decided 2026-05-26 · Terminology corrected

Permission Group = governs CRUD on org config (workflows, standards, invites, devices, billing). Each user is in exactly one. System groups: Owner, Admin, Member. Custom groups allowed.

Team = workflow grouping (Designers, Engineers, PMs). A user can be in many. Has no effect on org-config edit access. Workflows assign to users or to Teams.

Workflow assignment uses union — a user sees every workflow assigned to them OR any Team they're in. default: true per Team resolves tiebreaks; otherwise the orchestrator emits a decide step.

Updated model

Two axes, two tables, two questions answered.

PG Permission Groups
CRUD on org config · single membership
Every user is in exactly one Permission Group. Changing a user's group is one explicit action by an Admin. No precedence puzzle.
System + custom groups
Owner — full control + billing (system, immutable)
Admin — full control except billing (system, immutable)
Member — read-only on org config (system, default for new users)
Custom: e.g., "Workflow Editor" — write on workflows, read elsewhere
Custom: e.g., "Billing Approver" — read everywhere, write on billing
Why single membership
  • No precedence question — what you can do is obvious
  • Changing a user's role is one action, not "edit five groups"
  • Audit log entries are trivially attributable
  • Matches how org-config access is described to admins
Cost
  • Need custom groups for any nuanced role split
  • Can't compose access from multiple grants
T Teams
Workflow assignment · multi-membership
Teams are how an org models "Designers, Engineers, PMs." A user can belong to many Teams. Workflows assign to users or Teams. Teams have no effect on org-config edit access.
Example resolution
User: maya@acme
Permission Group: Member (read-only on config)
Teams: [Designers, Eng-Leads]
↓ workflow resolution
Workflows union: design-flow, eng-flow, eng-leads-only-flow
↓ task type matches 2
Pick the one marked default: true for Eng-Leads
If no default and ≥2 match → emit decide step
Why union
  • "More Teams = more workflows available" matches intuition
  • No "adding to a Team quietly removes access" failure
  • Single workflow can serve multiple Teams
  • Defaults give the orchestrator a deterministic pick
Cost
  • Authors must remember to mark a default per Team
  • The first time two workflows fight, the user gets a decide step
Schema impact org_members.permission_group_id — foreign key, NOT NULL. Replaces the old permission_group_members join.
teams(id, org_id, slug, name) + team_members(team_id, user_id) — many-to-many.
workflow_assignments(workflow_id, user_id?, team_id?, default boolean) — never references permission_group_id.
Permission Groups still own permission_grants(permission_group_id, resource_type, resource_id, action) for granular CRUD.
Documentation updated All references to "permission groups" in the context of workflow routing have been corrected across requirements-analysis.md, tech-stack.md, briefs/02-web-app.md, and the pitch deck. The web app brief now has separate sections for Permission Groups (CRUD) and Teams (workflow assignment).
