← Decision log ✓ Decided · Issue 15 · Generic items + type

Bugs are first-class.
But we don't want to duplicate the whole work pipeline.

The problem The original docs treated every piece of work as a "feature." That ignored bugs entirely. Software houses and agencies need both — and probably want Epics on top, and Spikes / Research later. Building separate parallel tables would duplicate the entire workflow / journal / decision infrastructure for each.
Decided 2026-05-26 · Generic items table with type discriminator

One items table. Each row has a type: feature, bug, or epic. One pipeline, one journal, one set of decisions, one dashboard surface. Type-specific UX (bug severity, feature user story, epic child list) is layered on the shared shape.

Future types — spike, task, research — drop in by adding a value to the enum, no schema changes. Workflows can target item types.

Implementation notes items(id, org_id, project_id, type, title, description, parent_id, status, owner_user_id, severity, user_story, created_at, archived_at). The severity column is required for bugs, null for others (enforced at app layer). user_story is feature-only. Workflows can target a type via their frontmatter (targets: [feature, bug]) and the orchestrator filters at dispatch time.
