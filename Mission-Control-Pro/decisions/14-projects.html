How do we identify a Project?
Software houses + agencies need this to work for both.

The problem Most orgs aren't building one product — software houses ship multiple products, agencies maintain many client projects. We need a Project entity that's elegant for both. The tension: free-form names are flexible but loose; git-repo identity is definitive but rigid (and excludes non-code work).
Decided 2026-05-26 · Hybrid (named + optional repo linkage)

A Project has a name (required) and an optional array of associated git repo URLs. Bridge auto-detects via .git/config on workflow start and offers to link the repo to the matching Project. Default UX is "name your Project"; git linkage is a power feature.

Supports monorepos (one repo linked to multiple Projects via path scoping — apps/web vs apps/api) and multi-platform Projects (one Project linked to many repos — "Mobile App" = iOS + Android + backend).

Decision

Project identity model — naming, git, or both?

A Decided
Hybrid — named with optional repo linkage
Project name is required. Repo URLs optional. Bridge auto-detects and suggests linkage. Monorepo support via per-repo path scoping. Multi-platform support via multiple repos per Project.
Schema shape
projects(id, name, slug, description, archived_at)
project_repos(project_id, repo_url, path?)
→ monorepo: many rows per repo, different paths
→ multi-platform: many rows per project, different repos
Pros
  • Default UX is naming — works for everyone
  • Auto-detection rewards git users without forcing it
  • Software houses, agencies, monorepos all model cleanly
  • Non-code work (research, design-only) still gets Projects
Cons
  • Slightly more schema (join table)
  • Auto-link suggestion flow needs UX care
B Not chosen
Free-form named Projects only
No git linkage at all. Just named entities — "Customer Portal," "Mobile App."
Simpler, less definitive
projects(id, name, slug)
no auto-detection
two repos could be mis-tagged
Pros
  • Smallest schema
  • Works for any kind of work
Cons
  • No auto-detection
  • No branch-tracking grounding
  • Naming inconsistency over time
C Not chosen
Git-repo defines Project
A Project IS its git URL. No separate naming. Forces git. Monorepos awkward.
Rigid identity
projects(repo_url PK, ...)
monorepo: awkward
renames: broken linkage
non-code: no Project possible
Pros
  • Definitive identity
  • Auto-detection trivial
Cons
  • Forces git on everyone
  • Monorepo support requires path hacks
  • Repo renames break the world
  • Non-code work locked out
Implementation notes Bridge reads remote.origin.url from .git/config on workflow start. Queries cloud for matching project_repos rows. If exactly one match → auto-attach session. If multiple matches (monorepo with overlapping paths) → web prompt next time user opens dashboard. If no match → "Attach to Project?" prompt with an "Add as new repo to existing Project" option. Path scoping (`path` column) is null by default; users only set it for monorepo sub-Projects.
