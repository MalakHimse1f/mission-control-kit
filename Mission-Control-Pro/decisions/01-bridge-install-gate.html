"Start" from cloud depends on a bridge running locally.
What happens when the bridge is offline?

The problem Neither Claude Code nor Cursor exposes a remote-trigger API. The only way to spawn a local session from the web app is via our bridge daemon. If the bridge isn't installed, isn't running, or the device is asleep, the cloud has nothing to talk to. We need a UX that handles every state without confusing new users or eroding trust.
Decided 2026-05-26 · Path C

Three-state Start button. Online → instant launch. Sleeping → wake-via-push. Not installed → install CTA. Data model adds devices.online, devices.last_seen, devices.wake_endpoint.

Decision

How should the web dashboard behave when a user taps "Start" and their bridge is unreachable?

A Not chosen
Hard gate — Start is disabled until bridge online
The Start button is greyed out for any user without a connected bridge. A persistent banner explains "Install your bridge to begin." No ambiguity about state.

checkout-redesign · spec stage
[ Start ] (disabled)
⚠ Install your bridge to enable
Pros
  • State is predictable
  • Zero support tickets about "Start didn't do anything"
  • Drives bridge install at onboarding
Cons
  • New users feel blocked immediately
  • PM/designer accounts see nothing until *someone* installs a bridge
  • No fallback for "I want to copy-paste a command myself"
B Not chosen
Soft fallback — command copy-paste when bridge is unreachable
Start is always enabled. If no bridge is online, a modal opens with the command the user would otherwise have gotten launched for them. They can copy-paste it into their terminal. Cloud picks the session up the next time the bridge connects.

Pros
  • Web is always useful, even pre-install
  • Power users prefer it
  • Works on machines we'll never run a daemon on (CI, VDI)
Cons
  • State diverges — cloud doesn't know if user ran it
  • "Did anything happen?" support tickets
  • Two flows to test, document, and maintain
C Decided
Hybrid — three explicit states, each with its own affordance
The Start button presents a different control depending on bridge state: online → instant launch; installed but sleeping → wake-via-push button; not installed → install CTA. Every state is acknowledged in the UI; no guessing.
Three states of the Start button
● Online — [ Start ]
○ Sleeping — [ Wake & start ]
— Not installed — [ Install bridge ]
Pros
  • UX is honest about every state
  • Wake-via-push converts most "offline" moments into "online"
  • One path, no parallel flows
Cons
  • Slightly more implementation (state machine + push)
  • Wake-via-push needs bridge to register a wake URL on install
Implementation notes if Path C is chosen The data model needs devices.online, devices.last_seen, and devices.wake_endpoint. The web app subscribes to devices realtime so the button state updates without reload. "Wake via push" uses the same Expo Push channel as decision notifications but with a silent payload that the bridge interprets as a TCP reconnect cue.
