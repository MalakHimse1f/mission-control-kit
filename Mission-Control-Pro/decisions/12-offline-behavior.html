Devs work offline (flights, café WiFi gaps).
What does the bridge keep doing?

The problem The agent runs on the dev's machine and doesn't need the cloud. But the cloud expects events. If the bridge can't reach the relay, what happens? Block work? Queue silently? Let the dev keep going and reconcile later?
Decided 2026-05-26 · Path B

Bridge blocks the agent when offline. Cloud visibility is a hard product requirement — "agents working invisibly" is not a state we tolerate. Tray shows "Offline — agent disabled" with a Pause Bridge action to stop retries during flights / VPN gaps. Marketing must not promise offline support; docs explain explicitly.

Decision

What's the offline contract for the bridge?

A Not chosen
Local-first — queue events, reconcile on reconnect
Agent keeps running. Bridge queues all events to local SQLite. On reconnect, it drains the queue in order. If a workflow version changed in the cloud during downtime, in-flight sessions stay on the version they started with.

B Decided
Block agent when offline
If the bridge can't reach the cloud, it refuses to spawn or attach. Forces all sessions to be cloud-visible at all times.

Read-only offline — agent runs, no journal queue
Agent works locally during outage but events are *dropped* (only the final state syncs on reconnect). No journal queue.

Implementation notes for Path B Bridge maintains a connection-state machine: Online → AttemptingReconnect → Offline → Paused. In Offline state, all spawn and attach requests respond with cloud-unreachable. In-flight agent sessions receive a signal to pause at the next decide step. Tray badge changes color in Offline state. Pause Bridge action stops retries to save battery on flights. Marketing copy must avoid promising offline support; status page becomes load-bearing for customer trust.
