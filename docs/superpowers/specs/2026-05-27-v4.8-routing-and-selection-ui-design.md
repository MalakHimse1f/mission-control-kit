# v4.8.0 — Clean Routing + Exemplar-Based Selection UI

**Date:** 2026-05-27
**Base:** `mc-kit-v4.7.1` (branch `v4.7.1-base`)
**Status:** Design — pending user review

---

## 1. Context & motivation

v5 was rolled back. On GitHub, `v4.7.1` is restored as the "Latest" release; the
v5.x releases remain but are no longer current. This spec defines **v4.8.0**, a
forward minor release from the stable 4.x line that keeps v5's genuine wins and
discards what broke.

**What v5 got wrong**
- **Broke skill backward-compatibility.**
- **Rigid, broken decision UI.** v5 added decision-diagram primitives
  (`mc-mini-frame`, `mc-flow-timeline`, `mc-arch-node`) rendered by
  `lib/v5/decision-visual-builder.mjs`, which picked each option's picture by
  **keyword-matching the option text** and drew abstract gray placeholder bars.
  The agent was explicitly forbidden from drawing the real UI ("You do not
  assemble these `<div>`s by hand — the CLI does it deterministically"). Result:
  when two options were "full-width form" vs "form in a modal", the matcher
  couldn't distinguish them and produced **two identical diagrams that didn't
  match the descriptions.** This is the root cause of the disaster.

**What v5 got right (keep)**
- **Audited, cleaner document routing** — task types map to a minimal doc set.
- **Shorter pickup prompts** — a pointer to on-disk state instead of ~30 lines of
  embedded rules.

## 2. Goals / non-goals

**Goals**
1. **Full backward compatibility** with all v4.7.1 skills (both `skills/` and
   `claude-skills/` trees) and bundled vendor design skills.
2. **Clean, efficient document routing** — one purpose per document; each
   orchestrator/subagent session is routed only the documents it needs; short
   pickup prompts.
3. **Simple, exemplar-based instructions** for UI / UX / engineering diagrams: a
   reusable template plus a few worked examples, with general "riff on these"
   guidance — not rigid components.

**Non-goals**
- No JS router (`mc-router.mjs`) or code-encoded manifest — routing is
  doc-only (markdown the orchestrator reads).
- No changes to skill names, contracts, or I/O shapes.
- Not reusing any `lib/v5/*` machinery.

## 3. Part 1 — Selection-UI system

### 3.1 The approach
Replace the entire rigid HTML template system (`wireframe.css` + fixed
`primitives`/`skeletons` + `RESEARCH-LAYOUT.md`) with an **exemplar** model:
the agent is given **one template + a few worked examples + short instructions**,
and generates self-contained HTML by drawing the real UI/diagram per option.

### 3.2 New files — `control/layout/selection/`
- **`template.html`** — the approved "decision deck" scaffold with placeholder
  content and a leading comment block stating the rules. The agent copies this
  and fills it in.
- **`example-ui.html`** — worked UI-placement decisions (device/screen
  schematics). *Validated in brainstorming.*
- **`example-engineer.html`** — worked architecture decisions (service topology,
  job execution) using box/arrow/DB schematics. *Validated in brainstorming.*
- **`example-ux.html`** — worked UX-flow decisions (screen-in-sequence
  schematics). Built during implementation following the same pattern.
- **`SELECTION-UI.md`** — short instructions (the quality bar + rules).

Approved prototypes live in `.superpowers/brainstorm/2447-1779908832/content/`
(`exemplar-deck-v2.html`, `exemplar-engineer-v1.html`) and are the visual source
of truth to port. `.superpowers/` is gitignored, so §3.3–§3.5 capture the
contract so it survives if that directory is cleaned.

### 3.3 Deck contract (DOM + behavior)
Self-contained HTML document (inline `<style>` + `<script>`; no external assets).

**Structure**
- `.deck-head` with optional `.pager` (`‹ Back` / `Next ›` + clickable progress
  `.dots`). Pagination is **optional**: a single-decision file omits the pager
  and renders one `.question`.
- One `<section class="question" data-qid data-q>` per decision; first has
  `.active`.
- Inside each: `<div class="grid" data-count="2|3|4">` → `data-count` drives the
  column layout (2-up, 3-up, 2×2 for four).
- Each option: `<div class="card" data-key data-label onclick="pick(this)">`
  containing a hand-drawn schematic (`.mf` device frame for UI, inline `<svg>`
  for engineering/architecture, screen-sequence for UX), an `.opt-key`
  ("Option A"), an `<h3>` label and a `<p>` description.
- **Cumulative answer dock** `.answer`: header label + "X of N answered" counter +
  **Copy all** button, and a `<pre>` showing every answered question as
  `Q: … / A: Option X — …` (unanswered shown as `[ not answered yet ]`).

**Behavior (generic JS, auto-discovers from DOM)**
- `pick(el)` selects one card per `.question` (single-select within a question).
- `go(±1)` / dot clicks paginate.
- The dock recomputes cumulatively across **all** questions on every change.
- `Copy all` writes the full answer block to the clipboard; falls back to
  selecting the `<pre>` text when `navigator.clipboard` is unavailable (e.g.
  inside the dashboard's sandboxed iframe).

### 3.4 Visual rules (codified in `SELECTION-UI.md`)
- **Black / white / gray only**; clean layout and typography; generous whitespace.
- **Always 2–4 options**, never 1, never >4.
- **Each option's mockup must visibly demonstrate what its description says** —
  the fidelity bar is the approved "app-shell schematic" level (real labels,
  recognizable chrome), not abstract bars. Two options must never render alike.
- The agent draws the schematics **by hand** in HTML/SVG — there is no
  keyword-matching builder.
- Answers return to the agent via **copy-paste** (standalone file, no server).

### 3.5 Dashboard integration
`control/scripts/dashboard-content.mjs` embeds feature HTML via
`<iframe srcdoc>` (`iframeSrcdoc()`), so self-contained selection pages render
unchanged — no inlining of external CSS required. Verify wireframe-card styling
still frames them acceptably; adjust `dashboard-template.mjs` only if needed.

### 3.6 Retire the rigid system
Remove (or stub with a deprecation pointer):
- `control/RESEARCH-LAYOUT.md`
- `control/layout/CATALOG.md`
- `control/layout/primitives/` (incl. `index.html`)
- `control/layout/skeletons/` (all 8 shells)
- `control/lib/research-layout.mjs` (+ `tests/research-layout.test.mjs`)
- `control/features/_template/explore/_example.html`
- `control/features/_template/layout/README.md` references

### 3.7 Repoint skills (both trees)
Update references from the old system to the new template/examples/instructions in
**`skills/` and `claude-skills/`**: `mc-mock`, `mc-explore`, `mc-layout`,
`mc-feature`, `mc`, `mission-control`. Also `control/tech-stack/LAYOUT-TARGETS.md`,
`control/ORCHESTRATOR.md`, `control/ADD-FEATURE-PIPELINE.md`,
`control/USER-QUESTIONS.md`, `control/SESSION-INTENT.md`, and the dashboard
scripts. Skill **names, inputs, outputs, and stop conditions stay unchanged.**

## 4. Part 2 — Document routing (lightweight, doc-only)

- Add **`control/ROUTING.md`**: a single manifest mapping task type
  (explore / research / prd / mock / plan / build / ux-decisions / ui / architecture)
  → the minimal `{ doc, why }` set that session loads, plus universal rules
  (decision capture, presenting research HTML). Markdown only — the orchestrator
  reads it; no JS resolver.
- Enforce **one purpose per document**; trim docs whose content overlaps.
- **Shorten the pickup prompt** (in the `mc` skill / `HANDOFF.md` flow) to a
  pointer: read on-disk `state.json`/`HANDOFF.md`, consult `ROUTING.md` for the
  current stage, load only those docs, dispatch.
- Audit `CONTEXT-PACKETS.md`, `ORCHESTRATOR.md`, `PIPELINE.md`,
  `ADD-FEATURE-PIPELINE.md`, `PROJECT-START-PIPELINE.md`, `INDEX.md` so routing
  lives in one place and isn't duplicated.

## 5. Part 3 — Backward compatibility

- Branch is the v4.7.1 base, so all 21 skills work today. The discipline:
  edit instruction text only; preserve skill `name`, inputs, outputs, stop
  conditions, and disk paths.
- Bundled vendor design skills (`design-research`, `ux-strategy`,
  `interaction-design`, `prd-generator`, `designer-skills`, …) are **untouched**;
  only the HTML they're told to *render* changes (now exemplar-based).
- Add a regression check that every skill id present at v4.7.1 still exists with
  the same frontmatter `name`.

## 6. Versioning & release

- Ship as **v4.8.0**. Update `package.json`, `kit-manifest.json`, and any
  embedded version strings. Tag `mc-kit-v4.8.0` and publish as Latest at release
  time.
- The deprecated v5.x releases are left in place (already de-listed as Latest).

## 8. Risks & open questions

- **Clipboard in iframe.** Copy may be blocked inside the dashboard's sandboxed
  iframe; mitigated by the select-all fallback. Standalone-file use is primary.
- **Migrations.** `migrations/4.7.0-*` / `4.7.1-*` reference the old research HTML
  layout. Confirm they're historical-only and won't run against 4.8 projects;
  add a `4.8.0-*` migration only if existing projects need their on-disk research
  pages reconciled (likely not — pages are regenerated).
- **Two skill trees drift.** `skills/` and `claude-skills/` must stay in sync;
  consider a check that flags divergence.
- **UX example.** `example-ux.html` is unbuilt; it follows the proven pattern but
  should get a visual review during implementation.

## 9. Success criteria

1. Generating a UI/UX/architecture decision produces a self-contained page where
   **every option's mockup is visibly distinct and matches its description** (the
   v5 "two identical diagrams" failure cannot recur).
2. A session's pickup prompt is a short pointer; the orchestrator loads only the
   docs `ROUTING.md` lists for the current stage.
3. Every v4.7.1 skill id still resolves with an unchanged contract; bundled design
   skills work unchanged.
4. Dashboard renders the new pages via `iframe srcdoc`.
