Routing Pipeline

Step 1 — Input
Pickup Prompt (buildPickupPrompt)
Exactly 2 sentences with an embedded taskType — a fresh agent has everything it needs to call the router.
Sentence 1Resume feature "user-onboarding" at stage ux (taskType: ux-decisions).
Sentence 2Read control/v5/features/user-onboarding/status.json and decisions.json, then call resolveRoute({ taskType: "ux-decisions", stage: "ux", slug: "user-onboarding" }) from lib/v5/mc-router.mjs to load the minimum context for this phase.
Step 2 — State Lookup
Orchestrator reads status.json + decisions.json
The pickup prompt names both files. status.json gives current phase & feature; decisions.json gives the decision log + any deferred questions.
Step 3 — Route Resolution
mc-router.mjs
6 task types: ui-implementation, ux-decisions, architecture, research, build, brainstorm.
stageToDefaultTaskType(stage) is the helper the pickup prompt uses to pick a sensible default per stage.
Each route carries a usageNote that the dispatch packet surfaces as instructions[].
resolved route
Step 4 — Selective Load
Document Store
Only relevant documents loaded into context
focused context packet
Step 5 — Dispatch
Subagent Execution
Receives only what it needs — fast, focused, accurate

ARCHITECTURE was split into two docs. control/v5/routing/ARCHITECTURE.md is for decision visualization — it loads on the architecture route alongside stack.json and the architecture-primitives template. control/v5/routing/ARCHITECTURE-MVVM.md is for build code structure rules (MVVM layering) — it loads only on the build route as scope: mvvm-rules. The two docs live on different routes by design so a UX-or-UI subagent never receives MVVM rules and a build subagent never re-reads decision visuals.

Non-canonical stages pass through. Dashboard buckets (needs-input, ready, in-progress, complete) and legacy values (mock, brainstorm) are not in PHASE_ORDER, so shouldDefer() trusts the caller and does not block. The orchestrator is expected to resolve a canonical phase first via currentPhase() from lib/v5/decision-gate.mjs before calling resolveRoute with a non-canonical stage.

controlRoot semantics — same everywhere

All v5 modules use the same controlRoot: the project root — the directory containing control/v5/, not control/v5/ itself. Doc paths in routes already include the control/v5/... prefix, so path.join(controlRoot, route.docs[i].path) always resolves correctly in resolveRoute (when verifyExists: true) and in buildPacket.
